# OziClock Backlog

This is the canonical work queue for planned OziClock changes. Product behavior and acceptance criteria remain authoritative in `REQUIREMENTS.md` and feature design documents. `FUTURE_FEATURES.md` is an idea envelope, not a commitment to implement every item.

## How We Use This Backlog

- Keep an item's ID stable across discussions, commits, and pull requests.
- Move an item to `Ready` only after its intended behavior and acceptance criteria are clear.
- Add or update requirement IDs before implementation when an item changes observable behavior.
- Keep only one status per item: `Candidate`, `Discovery`, `Ready`, `In Progress`, `Blocked`, or `Done`.
- Record dependencies and blocking decisions in the item rather than in source-code TODO comments.
- Move completed items to the archive at the bottom of this file.

Priorities describe sequencing, not severity:

- `P1` — product quality or correctness work to address next.
- `P2` — focused product improvement after P1 work.
- `P3` — larger optional capability requiring its own product slice.

## BL-087 Implementation and Verification — 2026-09-24

scenarios pass at native display scale 1. Pixel inspection of compact, capsule,
and square snapshots confirms a single opaque black pixel at straight outer
edges and internal joins at application scale 1. The supplied desktop screenshot
has two dark top rows and a one-column separator, so its mismatch is real but
is not reproduced by the current renderer snapshot. No separate macOS outline
implementation was found; the native adapter enables system shadow and window
alpha. Matched-settings desktop verification with that shadow remains pending;
do not attribute the screenshot to shadow or an older build without that check.

clock-strip gaps also occupy the same one-line inset rather than adding another
line. FemtoVG doubles the width only for the clip calculation, whose rectangle

renderer. Both installed and debug applications were running during inspection;
window-only captures do not include the surrounding system shadow and cannot
establish the cause of the user's two-row desktop outline. Keep compositor/shadow
and overlapping-window effects as hypotheses, not verified causes.

documentation validator pass after integration. Integration preserved both
branches' backlog entries: the colliding local Plan Month item is now BL-092,

## BL-013 Investigation — 2026-09-10

Confirmed with isolated native AppKit and Slint probes on macOS 26.6.2 (25G83), primary display 5120 × 1440, backing scale 1, visible-frame top at screen y=31. Production Rust/Slint and user settings were not changed. The Slint probe linked the existing project libraries; the resolved dependency sources are Slint 1.17.1 and winit 0.30.13.

- `app_window.slint` correctly declares `no-frame: true`. Normal native frame and content origins match; this is not a persistent invisible title bar or an outer/inner coordinate conversion error.
- Slint `event_loop.rs` handles `Resized` and `Occluded` by calling `WinitWindowAdapter::window_state_event()`, which calls `winit_window.is_maximized()`.
- winit `src/platform_impl/macos/window_delegate.rs::is_zoomed()` temporarily applies `NSWindowStyleMask::Titled | Resizable` before calling `isZoomed`, then restores the previous style. Restoring the style does not restore the original position.
- A diagnostic trace of `NSWindow::constrainFrameRect:toScreen:` in the isolated Slint process captured `window_state_event -> is_maximized -> is_zoomed -> set_style_mask -> setStyleMask -> AppKit frame constraint`. For a 31-point content height, the temporary titled frame became 63 points high; AppKit moved its origin down by 32 points. Removing the title left the borderless window at y=63.
- Minimal Slint reproduction: a frameless, always-on-top 601 × 31 window, preferred height `62 - 31 * progress`, min/max heights 31/594, initial position (170,31). At the first timer callback its actual position was (170,63). Place it at (170,31) once to model the user's drag, then change progress and request increasing inner heights. After the first resize event the position becomes (170,63), with `decorated=false` and equal inner/outer origins. The timer only sequences and measures the diagnostic; it is not a proposed fix.
- Native A/B reproduction: an ordinary visible borderless NSWindow preserves its top edge through `setContentSize(601,62)`, including floating level and winit-equivalent main/key-window overrides. Adding only winit's temporary titled-style query moves it down by exactly 32 points. This isolates the cause from OziClock's drag logic, animation, settings persistence, and renderer.

Fix direction: repair maximized-state observation at the winit/backend boundary so reading state never mutates native style or geometry. For OziClock's clock strip, which has no native maximize behavior, a narrowly scoped Slint backend capability policy can avoid that query; a general winit repair must preserve actual maximize/restore semantics for other windows using explicit state tracking and reconciliation. Select and regression-test the dependency patch before production integration; do not globally return false for every window. A pinned source patch is reproducible; editing the local Cargo registry is not. The inspected upstream winit master still contains the temporary-style query, so an unverified version upgrade is not a demonstrated fix.

Rejected directions: title-bar-height adjustments or an additional borderless flag (already correctly configured); delayed/periodic position restoration; replacing resize with native `setFrame` alone (Slint still queries state on resulting events); disabling AppKit screen constraints; runtime method swizzling (used only to obtain diagnostic stack evidence). No framework replacement is justified by this finding.

Acceptance for implementation: state queries must leave both style and frame unchanged; startup and repeated compact/standard/ruler transitions at the work-area top must preserve the chosen position; verify 85%/100% clock scales, Retina and multi-monitor placement, and actual logout/login separately. Startup and resize were reproduced, but no user logout/login was performed. Keep the issue open until the patched application passes these checks and the required debug launch.
